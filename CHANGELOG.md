### Added
- **Docker AuthZ plugin** (task H07, ADR-M105, QUESTIONS #656–#660): shared create-body denylist (`@sdlc/docker-authz`) used by `docker/guard.ts` and a legacy AuthZ plugin on the runner Engine; host install scripts; `pnpm doctor` check `runner.authz`; live probe in `pnpm test:runner` on rootless CI. Closes ADR-M80 gap G-7's body-check mitigation.
- **Client data deletion, part 1** (task H03a, ADR-M97 §2): tenant states `pending_deletion` and `purged`; `TenantScope.clientDataDeletion.anonymizeUser` / `scrubProjectConfigs` scrub people and project YAML in place so foreign keys and append-only tables stay intact.
- **Client data deletion, part 2** (task H03b, ADR-M97 §2): `runClientPurgePass` in the retention loop. After `SDLC_CLIENT_DELETION_GRACE_DAYS` from `client_data.deletion_approved`, it revokes access, purges evidence (GOVERNANCE bypass), Langfuse and knowledge for finished not-held intents, anonymizes people, writes `client_data.deleted`, and sets the tenant to `purged`. An open intent or active hold records `client_data.purge_blocked_by_hold` and blocks completion.
- **Client data deletion, part 3** (task H03c, ADR-M97 §2.4): tenant admins `adlc client request-data-deletion|cancel-data-deletion|status` through `/v1/client/data-deletion`; operators `adlc ops client-data-deletion approve|list|status` (two-person rule: `--operator` ≠ requester). Approve sets `pending_deletion`; cancel during the grace period restores `active`. Tokens of a `pending_deletion` tenant may call only the data-deletion routes and `GET /v1/me`.

### Changed
- H07 live runner tests on an AuthZ Engine: create stub networks with `--internal`; seed knowledge-db via `docker create`/`cp`/`exec` (no binds or published ports); host listeners for egress probes run in the test process instead of `--network host`; rootless CI enables the containerd image store so fixture builds keep local digests without publishing a registry port; `runner-approle-init` drops CapAdd (AuthZ denylist) and delivers AppRole files as root with default capabilities.

- The run's MCP gateway is now agentgateway **1.7.0** (pinned by digest): 1.6.0 carries a CRITICAL finding in `ca-certificates-bundle` (CVE-2026-91403). The generated gateway configuration sets `config.session.key: disabled`, because 1.7 otherwise writes a session key it makes into the run's config volume; MCP sessions stay unencrypted, as in 1.6 (PR #496).
- **A simpler release** (ADR-M104, `RELEASING.md` 3.0). The owner merges the version pull request; nothing else. The environment `npm` has no required reviewer any more: the merge is the release decision, and npm publishes after the same checks (ADR-M104 1.1). CI runs the upgrade test on a version pull request by itself. `release-tag.yml` tags the merge commit and starts `release.yml` on the tag; for that the tag ruleset blocks updates and deletions but no longer creation (the owner's setting; turn "Restrict creations" on again before giving anyone else write access). `pnpm release:prepare X.Y.Z` prepares the version pull request and refuses without Upgrade notes under `[Unreleased]`, which each pull request now writes (rule R146).

## [0.11.0] - 2026-10-31

**Operations on a server, part 2: key rotation (O05) and data that only grows (O04).** The Run Contract signing key rotates by itself every 90 days, and one command renews every AppRole secret ID. `pnpm doctor` and `pnpm alerts` now warn 14 days before a secret ID ends and when an append-only table grows large. The worker removes the dashboard's old sessions and passkey challenges. `run_events` are kept at least 2 years, like every append-only table.

### Upgrade notes
- **On a running stack:** (1) `pnpm install`; (2) `pnpm compose:env --add-missing`: it appends `SDLC_APPROLE_WARN_DAYS`, `SDLC_DB_TABLE_WARN_GB`, `SDLC_WORKER_HOUSEKEEPING_MODE`, `SDLC_WORKER_SESSION_KEEP_DAYS` and `SDLC_WORKER_CHALLENGE_KEEP_HOURS` with their defaults; (3) `pnpm db:migrate`: migration `0046-housekeeping`; (4) `pnpm openbao:bootstrap configure` once more, with a root token from two key holders (README "Upgrade" step 8): it sets the signing key's rotation period (`TRANSIT_AUTO_ROTATE_PERIOD`, 2160h); no credentials command to run again; (5) on a checkout of the tag `v0.11.0` the published images are pulled (`pnpm images mode`); on any other checkout rebuild `sdlc-api`, `sdlc-worker` and `sdlc-runner`, and deploy the three together; (6) start the platform again as usual (`platform/deploy/scripts/up.sh …`): volumes are kept.
- **Old sessions go on the first pass:** the retention loop now runs also without the evidence identities. Its first pass removes web sessions that ended more than 30 days ago and passkey challenges older than 24 hours, and writes one `housekeeping.removed` (counts) per tenant that had some. `SDLC_WORKER_HOUSEKEEPING_MODE=report` only counts; `off` stops it.
- **`pnpm doctor` may show two new warnings:** an AppRole secret ID older than 76 days (renew them all with `pnpm openbao:bootstrap rotate-credentials`, in your terminal; runbook T11 §8.1), and an append-only table over 20 GiB (deploy README "Database growth").
- **A trial stack** set up before this release keeps working. Its signing key gets the rotation period only after `pnpm trial:down --wipe` and `pnpm trial:up` (a trial stack has no root token to run `configure`). Nothing else is needed.
- The command: `npm install -g @hoanghainh/governed-adlc@0.11.0`.

### Added
- **Housekeeping of the dashboard's sessions** (task O04, ADR-M103, migration `0046-housekeeping`). The worker's retention loop removes web sessions 30 days after they ended (`SDLC_WORKER_SESSION_KEEP_DAYS`, at least 7) and passkey challenges 24 hours after use or expiry (`SDLC_WORKER_CHALLENGE_KEEP_HOURS`, at least 1). It does this only through two definer functions; the database refuses any other removal. Each tenant with removals gets `housekeeping.removed` (counts). `SDLC_WORKER_HOUSEKEEPING_MODE`: `remove` (default), `report`, `off`.
- `pnpm doctor` checks the size of the append-only tables (`db.table_size`) and warns at `SDLC_DB_TABLE_WARN_GB` (20 GiB), so `pnpm alerts` tells the operator long before partitions are needed. Deploy README "Database growth".
- **Key rotation** (task O05, ADR-M102). The Run Contract signing key now rotates by itself every 90 days: `configure` sets `auto_rotate_period` from `TRANSIT_AUTO_ROTATE_PERIOD` in `bootstrap.conf`. Contracts signed before keep verifying until they expire. Runbook T11 §8.4 explains how to revoke a doubtful key version with `min_decryption_version` and how to check that no unexpired contract still uses it.
- `pnpm openbao:bootstrap rotate-credentials` renews every AppRole secret ID that is set up (api, worker with cost-controller, runner, LiteLLM sidecar, backup) with one admin token. Owner's terminal only.

### Changed
- `pnpm doctor` (and so `pnpm alerts`) warns 14 days before an AppRole secret ID ends, not 10 (`SDLC_APPROLE_WARN_DAYS`), and names `rotate-credentials` as the fix.

## [0.10.0] - 2026-10-30

**Operational alerts (O03), and the old command name `sdlc` is gone.** `pnpm alerts` tells the operator, by a chat webhook or e-mail, when a service is not healthy, OpenBao is sealed, a disk or the backup target fills up, a backup did not run or a certificate nears its end. `pnpm doctor` gains the check `backup.recent`. As announced in 0.9.0, only `adlc` is installed now.

### Upgrade notes
- **On a running stack:** (1) `pnpm install`; (2) `pnpm compose:env --add-missing`: it appends the new optional keys `SDLC_BACKUP_WARN_HOURS`, `SDLC_BACKUP_FAIL_HOURS` and `SDLC_ALERT_*`, empty or with their defaults; nothing else changes until you set a channel; (3) no migration and no credentials command to run again; (4) on a checkout of the tag `v0.10.0` the published images are pulled (`pnpm images mode`); on any other checkout rebuild `sdlc-api`, `sdlc-worker` and `sdlc-runner` and deploy the three together; (5) start the platform again as usual (`platform/deploy/scripts/up.sh …`): volumes are kept.
- **`pnpm doctor` may now warn about backups:** on a server with `SDLC_BACKUP_DIR`, the newest complete backup older than 26 hours is a warning and older than 50 hours a failure. Without `SDLC_BACKUP_DIR` the check is skipped.
- **Alerts (optional, on a server):** put the webhook URL alone in a file of mode 600 and set `SDLC_ALERT_WEBHOOK_FILE`, or set `SDLC_ALERT_EMAIL_TO`; then `pnpm alerts --test`, and install the timer `platform/deploy/alerts/sdlc-alerts.timer` (deploy README "Alerts", runbook T11 §6b).
- **The command:** `npm install -g @hoanghainh/governed-adlc@0.10.0`. **`sdlc` is removed**: write `adlc` in every script, and `pnpm adlc …` instead of `pnpm sdlc …` in a checkout. Your login stays: `adlc` still reads one that `sdlc` saved in `~/.config/sdlc/`. Coming from `agentic-sdlc-cli`: `npm uninstall -g agentic-sdlc-cli` first.
- **The trial:** `pnpm trial:up` now refuses at the start without OpenSSL 3 as `openssl` (on macOS: `brew install openssl@3`, then put it first on the `PATH`). A running trial stack is not affected.

### Removed
- **The old command name `sdlc`** (ADR-M100, as announced in 0.9.0): the npm package installs only `adlc`, and a checkout has only `pnpm adlc` (no `pnpm sdlc`). The note `sdlc` printed is gone. `adlc` still reads a login that `sdlc` saved in `~/.config/sdlc/`.

### Added
- **Operational alerts: `pnpm alerts`** (task O03, ADR-M101). It runs the checks of `pnpm doctor` on the server and sends what changed to the operator: a chat webhook (the URL in a file of mode 600, `SDLC_ALERT_WEBHOOK_FILE`; formats `text` for Slack, Google Chat, Mattermost and Rocket.Chat, or `json`), e-mail through the server's `sendmail` (`SDLC_ALERT_EMAIL_TO`), or both. A problem is sent when it is new or changes, again every 24 hours while it stays, and as "resolved" when it is fixed. A message holds the host, the check, its subject, doctor's text and fix: never a secret, an env value or a log line. It works while the platform is down or OpenBao is sealed. `--test` sends a test message, `--dry-run` shows what would be sent. The server's timer runs it: `platform/deploy/alerts/sdlc-alerts.service` and `.timer` (every 10 minutes), or cron. Deploy README "Alerts", runbook T11 §6b.
- `pnpm doctor` checks that a backup ran: `backup.recent` reads the newest complete folder in `SDLC_BACKUP_DIR` and warns after `SDLC_BACKUP_WARN_HOURS` (26), failed after `SDLC_BACKUP_FAIL_HOURS` (50).

### Fixed
- `pnpm trial:up` ended with "Use pnpm sdlc as usual", and `adlc help` started with "sdlc:". Both now say `adlc`. A test checks that no message of the catalog tells a person to run the old command; only the note of `sdlc` names it (ADR-M100).
- `pnpm trial:up` refuses at the start when `openssl` is missing or is not OpenSSL 3 or later (on macOS, `/usr/bin/openssl` is LibreSSL). Before, it stopped at step 2 (`init-env.sh`), after the passphrase was typed twice.

- V17 (QUESTIONS #617, #618): `sdlc admin project apply --file project.yaml [--dry-run] [--yes]`, a project and its team from one YAML file instead of about 15 `sdlc admin` commands (deploy README steps 9, 11, 12). The file holds the project, the team (e-mail, name, GitHub login, roles), the agent to register and the configuration that differs from the defaults; its schema `projectFileSchema` is in `@sdlc/api-schemas` and refuses any unknown key, so no secret goes in. It never revokes a role, changes a registered agent, approves the agent, writes the AI record, issues a token or gives the operator a role; it prints those commands per person. Handbook Ch.19 §19.8d.
- H03 (ADR-M97, accepted; QUESTIONS #611–#615): design for deleting a client's data on request under Japan's APPI or contractual terms. Defines taxonomy of purged vs retained data: evidence files in SeaweedFS, Langfuse traces in ClickHouse/OTLP store, and knowledge vector schemas are hard purged; personal identifiable information (PII) in the `users` table is anonymized in-place (`deleted-<id>@redacted.invalid`) to preserve foreign keys; immutable append-only tables (`audit_log`, `gate_decisions`, `run_events`, `cost_records`) and cryptographic hash chains are retained intact for at least 2 years without any row deletion or modification. The deletion is recorded as the terminal audit event (`client_data.deleted`) in the tenant's hash chain. Protected by Two-Person rule (Tenant Admin + Platform Operator), a mandatory 14-day grace period, and active legal hold blocking. Decomposes follow-up implementation into tasks H03a, H03b, and H03c.
- H02 (ADR-M96, accepted; QUESTIONS #606–#608; ADR-M80 gaps G-1, G-5): dependency scanning outside the sandbox. The runner scans the staged manifest and lockfiles (`package.json`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`) outside the sandbox before pushing. Verifies licenses against project allowed list (`dependencies.allowed_licenses`), flags install scripts (`preinstall`, `install`, `postinstall`, `requiresBuild: true`), checks for typosquatting against popular packages using Levenshtein distance, and flags blocked packages. The run event `dependencies_scanned` holds codes and counts only. Any unapproved license, install script, or typosquatting warning forces G6 to HITL with `dependency_finding`. Blocked package advisory findings pause G6 with a `security` escalation to Person B. Verdaccio npm proxy disables uplink cache (`cache: false`) to prevent inter-tenant cache poisoning (ADR-M80 gap G-5). Migration `0044-dependency-checks` adds `dependency_finding` and `dependency_scan_failed` to `gate_reason_code`. Handbook Ch.14 §14.10.2.
